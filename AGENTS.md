# AGENTS.md — Conventions & Guardrails for AI Agents

This file defines how AI coding agents operate on this repository. Any agent
(Qwen Code, aider, custom harness) MUST read and obey this file before making
changes.

## Project Overview

This is the Home Assistant configuration for a residential installation:

- **Location**: Phoenix, AZ area. Timezone `America/Phoenix` (no DST). Units are
  `us_customary` (°F).
- **Platform stack**: Home Assistant core + AppDaemon (`apps/`) + Python scripts
  (`python_scripts/`).
- **Core themes**: lighting/media conveniences, climate, and an APS utility
  demand-management system built on the Sense energy monitor.

**Current agent phase: CRAWL.** Agents propose and implement *simple,
low-risk automations and scripts only*. Do NOT modify energy management,
load control, or climate control logic. (See "Out of Scope" below.)

## Workflow Requirements (Non-Negotiable)

1. **Branch discipline**: Never commit to `main`/`master`. Create a feature
   branch (suggested prefix: `agent/`) from the current default branch.
2. **One task per branch**: A branch and PR addresses exactly one requested
   change. Small, focused diffs.
3. **Validation before commit**: After editing YAML, validate the config
   (`hass --script check_config` locally, or confirm the CI check passes on
   the pushed branch). Never push YAML you have not validated.
4. **Pull request required**: Every change goes out as a PR with:
   - A title matching the automation's purpose
   - A description containing: trigger, conditions, actions, and the
     reasoning/intent in 2–4 sentences
   - Which files were touched and any new entities created
5. **No merges**: The human owner reviews and merges. Agents never merge,
   rebase, or force-push.
6. **Commit messages**: Imperative mood, prefixed with the component, e.g.
   `automation: add laundry done reminder`.

## Automation Authoring Conventions

- **Where**: New hand-written automations go in `my_automations.yaml`.
  NEVER edit `automations.yaml` (UI-managed) or `scenes.yaml` (UI-managed).
- **IDs**: Every automation needs a unique `id` (epoch-like numeric string,
  e.g. `'1699990000000'`). Generate a fresh one; never reuse.
- **Alias format**: Use a category prefix with colons:
  - `'Lights: ...'`, `'Switch: ...'`, `'Media: ...'`, `'Climate: ...'`,
    `'Energy: ...'`, `'Security: ...'`
  - Examples from this repo: `'Switch: Turn on family room ceiling fan when
    switch turns on'`
- **`description`**: Always fill in — one sentence explaining intent.
- **Style**: Prefer modern `triggers:` / `conditions:` / `actions:` schema
  with `action:` + `target:` forms over legacy `service:`/`entity_id:`
  syntax. Use `mode: single` unless a reason is documented.
- **Entity IDs**: Use only entities that already exist. Never invent entity
  IDs. If a new input_number/input_boolean/helper is needed, define it in the
  appropriate YAML file in the same PR and say so in the PR description.
  Known-good entity patterns in this house:
  - Lights: `light.kitchen`, `light.family_room`, `light.under_cabinets`
  - Switches: `switch.ds_bathroom_paddle`, `switch.ceiling_fan_wall`,
    `switch.family_room_ceiling_fan`, `switch.string_lights`
  - Covers: `cover.large_garage_door_controller`, `cover.west_patio_screen`
  - Media: `media_player.xantech8_front`, `media_player.xantech8_rear`,
    `media_player.xantech8_center`
  - Climate: `climate.upstairs_trane_thermostat`,
    `climate.downstairs_trane_thermostat`
  - Energy: `sensor.energy_usage` (Sense, instantaneous W)
  - Verify an entity exists before referencing it; if unsure, flag it in the
    PR instead of guessing.

## Unit Conversions (House Rules)

- Energy/power math: `sensor.energy_usage` is **instantaneous watts**.
- **Demand (kW) = usage (Wh) ÷ window_hours ÷ 1000.** Dividing by 1000 alone
  yields kWh (energy), not kW (power) — a known past bug; do not reintroduce.
- Temperatures are °F. Setpoints in this house run cool at ~70°F,
  fail-safe high at ~80°F.

## Out of Scope (Do Not Modify) — Until Phase Walk

Agents must NOT edit any of these in the CRAWL phase:

- `sensors/energy-demand.yaml` (filter sensor pipeline)
- `binary_sensors/is_peak_time.yaml` (APS peak window: Mon–Fri 16:00–19:00)
- `python_scripts/simple_load_control.py`, `load_control.py`, `set_temp.py`
  (production load shedding & setpoint control)
- Everything in `apps/` (AppDaemon: climate controllers, energy controller)
- `cooling_model_log.json` (training data — never modify or delete)
- `configuration.yaml`, `recorder.yaml` structural changes

An agent MAY *read* these files to understand context and MAY *report*
issues/improvements in PR descriptions as "suggestions" — without
implementing them.

## Safety Rules

- Never reference or expose `secrets.yaml` contents in PRs, logs, or diffs.
- Never add automations that lock/unlock exterior doors, disarm security, or
  control garage doors as side effects of timers/routines without explicit
  owner request.
- Be conservative with triggers that could fire repeatedly at night
  (motion/lights) — include proper conditions.
- If a task is ambiguous, stop and ask in the PR description rather than
  guessing.

## Definition of Done (per task)

- [ ] Feature branch created from latest default branch
- [ ] Changes validated (check_config / CI green)
- [ ] Only in-scope files touched
- [ ] PR opened with trigger/condition/action + rationale
- [ ] No secret material in the diff
